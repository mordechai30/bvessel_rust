# Product checks and verification limits

## Build matrix

- Distinguish installed compiler, rust-version, edition, style edition, and deployment targets. Verify
  actual API stabilization; do not turn an inspected compiler version into a project requirement.
- Test MSRV with dependency resolution, lockfile format, build scripts, proc macros, and enabled features.
  Check libraries against consumer resolution when their own lockfile would hide compatibility problems.
- Use supported default/minimal/backend/target/profile configurations, not a universal all-features union.
  Inspect Cargo feature unification and resolver behavior; one no-default-features edge cannot disable
  another.
- Keep normal/build/dev dependencies separate; distinguish build-host proc macros from target code.
- Preserve check-only hooks and core.hooksPath. Use cargo fmt --all -- --check and supported workspace
  Clippy with --locked and warnings denied for a valid configuration; do not rewrite staged code in hooks.
- Scope justified lint allowances. Run doctests separately from nextest; retain an existing Cargo test
  workflow.

## Checks by contract

- Compile public API use from an external crate; test intended borrow/trait rejection with compile-fail cases.
- Test parser truncation, overflow, malformed encoding, unknown tags, maximum lengths, and partial records.
- Test concurrent limits as observed counts/bytes and completed destruction, not only successful outputs.
- Exercise cancellation at suspension points and actual partial progress; retain errors from cleanup.
- For unsafe, review invariants plus valid safe-client boundary cases: empty/ZST, alignment, panicking
  initialization, repeated transfer, and permitted misuse attempts. Do not execute deliberate UB in normal
  tests.
- Use focused Miri/sanitizers or bounded Loom models where supported; report unsupported paths. They do
  not prove complete soundness, all schedules, arbitrary foreign behavior, or every target ABI.
- Label pseudocode, compile-only helpers, executed tests, and historical results accurately. Assertions
  inside an uncalled helper do not establish runtime verification.

## no_std and target constraints

- Check transitive default features for accidental std use, allocator requirements for alloc, capacity
  exhaustion, panic behavior, and target atomic support. no_std does not imply no allocation or real-time
  bounds.
- Use target contracts for interrupts, critical sections, DMA, MMIO, cache coherence, and thread affinity.
  Volatile access does not provide synchronization. Measure worst latency including destructors and
  contention.

## Retained fixtures

Run fixtures only when relevant. They are copied contract examples, not required product architecture.
Resolve paths from the skill root; execute shell commands/scripts outside sandbox restrictions.

- Compile examples/contracts-std.rs with rustc --edition=2024 --test into a temporary output, then run it.
- For examples/contracts-async.rs, use an isolated temporary Cargo package with that file as its library.
  Select project-compatible Tokio 1 with rt, macros, sync, time, io-util, and test-util features; run cargo
  test.
- Do not add these test dependencies to the user's project merely to exercise the skill's fixtures.
- Preserve fixture-level owner/supervisor preconditions; canceling the supervising future cannot await
  cleanup.
- Recheck examples against the actual MSRV before adopting APIs. A fixture pass is not a proof of the skill.
